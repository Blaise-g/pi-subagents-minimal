# Generic Subagent and Selectable Capabilities Proposal

Status: **Historical, superseded design proposal**

Normative implementation specification: [Canonical implementation contract](v1-implementation-contract.md)

Approved decision source: [GitHub issue #40](https://github.com/Blaise-g/pi-subagents-minimal/issues/40)

Proposed dogfood release: `pi-subagents-minimal@0.2.0`

Affected repositories: `pi-subagents-minimal`, `pi-web-access-minimal`, and the maintainer's parent orchestration skills

This proposal records the design before independent review. Issue #40 incorporated the accepted review findings and final grilling decisions; the canonical implementation contract now controls wherever they differ.

## 1. Review objective

This document proposes a pre-v1 correction to the public Task model. It is deliberately detailed so an independent reviewer can challenge the domain model, capability boundary, integration design, migration plan, and evidence strategy before the canonical contract or executable code changes.

The reviewer should not assume this proposal is approved. Structured feedback is requested in section 17.

## 2. Current project context

`pi-subagents-minimal` is a personal, deliberately narrow Pi extension for isolated background Subagents. Version `0.1.0` is globally installed from a mutable local checkout for dogfooding; it is not published. Stable `1.0.0` remains a future target.

Canonical current sources are:

- `CONTEXT.md`: domain glossary;
- `docs/spec/v1-implementation-contract.md`: approved current implementation contract;
- `docs/adr/0001-keep-model-evaluation-outside-release-automation.md`: evaluation policy;
- `agents/investigation.md`: exact current package-owned Agent definition;
- `docs/release-evidence.json`: deterministic assertion-to-evidence inventory;
- GitHub issue #5: current instruction-ownership decision;
- GitHub issue #9: historical four-workflow scenarios and rationale; its Behavioral battery was superseded and must not be restored as a release gate;
- GitHub issues #18 and #33: stable package implementation/publication tracking.

The current extension admits one Task or a Flat batch of independent Tasks, starts isolated in-memory child Pi sessions in the background, persists a bounded Terminal envelope before notification, and supports inspect/cancel through `delegation_control`.

The current Task schema is:

```ts
type TaskSpecification = {
  agent: "investigation";
  task: string;
  model?: `${string}/${string}`;
  thinking?: ThinkingLevel;
  reportPath?: string;
};
```

Every child currently receives `read`, `grep`, `find`, and `ls`. A Task with `reportPath` additionally receives a closure-bound `write_report` tool for exactly that declared Markdown destination beneath `artifacts/`.

## 3. Problem statement

The public schema conflates two concepts:

1. a fixed execution profile that establishes isolation, capability discipline, evidence quality, truthful reporting, and report behavior;
2. a temporary task role supplied by a parent workflow, such as Explorer, Researcher, Standards reviewer, Spec reviewer, Reuse reviewer, Quality reviewer, or Efficiency reviewer.

The only public `agent` value is `"investigation"`, so it is not a real selector. It nevertheless implies that every child has an Investigation role. This is natural for exploration and research but misleading for review and simplification Tasks whose roles are owned by external parent skills.

The current capability set is also insufficient for the intended workflows:

- `code-review-diff` expects reviewers to inspect a Git diff from a fixed point;
- `code-simplify` expects reviewers to inspect the working-tree diff;
- evidence-intensive research may need external web search and primary-source retrieval;
- selected reviews may need to run checks.

Without Bash, review Tasks must rely on the Orchestrator embedding a diff, which duplicates context and may exceed Task limits. Without web tools, research is local-only even when the parent workflow requires external primary sources.

The README currently names review and simplification as supported integrations, so this mismatch must be resolved or those claims narrowed.

## 4. External design comparison

The repository previously evaluated exact published versions of three broader packages in `.worktrees/candidate-designs/docs/research/candidate-subagent-designs.md`.

### Nico Bailon `pi-subagents@0.57.0`

`agent` selects a genuine discovered definition. The package ships specialized roles such as scout, researcher, reviewer, and worker. Definitions own system prompts, tools, model settings, and other policy. This is a role catalog and broad orchestration platform.

### Tintinweb `@tintinweb/pi-subagents@0.18.2`

`subagent_type` selects discovered project/global/default Agent definitions. Specialized definitions own their system prompts and tool configuration. Parallelism commonly comes from multiple Agent calls.

### Arhen `@arhen/pi-core-subagent@1.3.46`

The caller usually invents an `agent` label and may pass an inline system prompt and arbitrary tool choices. A fuzzy-matched local Agent file may replace that inline definition. This is flexible but gives the caller broad role/capability authority and has surprising substitution semantics.

### Proposed distinction

This package should use none of those authority models. It should have:

- no public Agent catalog;
- no arbitrary system prompt;
- no arbitrary tool forwarding;
- one fixed generic Subagent execution profile;
- a bounded Task string that supplies the temporary analytical role;
- a closed package-owned list of selectable additional capabilities.

## 5. Proposed domain model

### Subagent

An isolated child Pi session that completes one bounded Task with an explicit capability set. “Subagent” names the execution entity, not a task-specific personality.

### Subagent definition

The exact package-owned Markdown instructions that establish durable child discipline. The proposed file is `agents/subagent.md`. It does not define the child as a Researcher, Explorer, or Reviewer.

### Task specification

The parent-authored request containing the concrete objective, temporary analytical role or lens, bounded scope, useful starting points, evidence requirements, answer requirements, execution selection, and optional report destination.

### Task role

The temporary analytical responsibility expressed in `task`, such as Standards reviewer or external-source Researcher. It is not a discovered Agent definition and grants no capability.

### Base capabilities

The tools every child receives: `read`, `grep`, `find`, and `ls`.

### Additional capability

One caller-requested capability from a closed package-owned enum: `bash`, `web_search`, or `fetch_content`.

### Derived report capability

`write_report`, supplied only when a valid `reportPath` is declared. It is not caller-selectable through `tools`.

### Effective tools

The complete canonical list actually supplied to a child: base capabilities, requested additional capabilities, and the derived report capability.

## 6. Proposed public Task schema

```ts
type AdditionalTool =
  | "bash"
  | "web_search"
  | "fetch_content";

type TaskSpecification = {
  task: string;
  tools?: AdditionalTool[];
  model?: `${string}/${string}`;
  thinking?: ThinkingLevel;
  reportPath?: string;
};
```

Changes from `0.1.0`:

- remove `agent: "investigation"`;
- add optional `tools`;
- preserve `task`, `model`, `thinking`, and `reportPath`.

`tools` contains additions only. Callers do not repeat base tools. Omission and `[]` are equivalent. Duplicate names are rejected rather than silently deduplicated. Unknown names fail whole-request preflight.

Canonical effective-tool order is proposed as:

```text
read, grep, find, ls, bash, web_search, fetch_content, write_report
```

Only present tools appear. Caller order never changes execution or persisted output.

## 7. Task prompting contract

`task` remains one opaque bounded string. The extension validates deterministic representation and size, not semantic prompt quality. The exact string is passed unchanged as the child user message with prompt-template expansion disabled.

A well-framed Task should contain only relevant task-specific material:

1. concrete objective or reviewer lens;
2. bounded scope or fixed point;
3. useful starting points;
4. required evidence;
5. answer or report requirements;
6. material constraints specific to that Task.

Generic capability, truthfulness, evidence, report-write, nested-delegation, and scope-discipline policy belongs in the package-owned Subagent definition and should not be repeated in every Task.

The extension must not attempt semantic prompt linting. Heuristics cannot reliably determine whether a concise Task has a valid objective or whether a role prompt is high quality. Parent skills remain responsible for constructing Tasks.

This follows the retained GPT-5.6 prompting research in `docs/research/gpt-5-6-codex-subagent-guidance.md`: keep prompts lean, state each instruction once, expose only task-relevant tools, define scope and success criteria, and evaluate model/Thinking choices rather than assuming stronger settings help.

## 8. Proposed generic Subagent definition

The current opening instruction:

> Investigate only the bounded Task specification.

should become:

> Complete only the bounded Task specification.

The durable definition should require the child to:

1. complete only the bounded Task;
2. gather and evaluate evidence before concluding;
3. distinguish findings or facts, recommendations, and uncertainty when material;
4. use only supplied capabilities and never attempt nested delegation;
5. avoid intentional repository mutation unless a future explicit mutation contract authorizes it;
6. return the concise requested answer when no report is declared;
7. complete exactly one successful `write_report` call when a report is declared, then return only a concise summary and path;
8. cite exact paths, symbols, local sources, commands, or external sources when requested;
9. never claim access, execution, writes, or verification that did not occur;
10. stop when the requested answer is established.

It must not call the child an Investigator, Researcher, Explorer, or Reviewer. Those are Task roles.

## 9. Capability semantics

### Base local inspection

All children receive `read`, `grep`, `find`, and `ls`. This remains the least-authority default.

### Bash

`bash` is a Pi built-in and can be selected directly when creating the child session. It supports Git inspection, tests, and checks.

Bash is not read-only or sandboxed. It can modify files, invoke network clients, access credentials available to the host process, and execute arbitrary programs. A system-prompt prohibition against intentional mutation is behavioral discipline, not technical enforcement.

Therefore the revised documentation and contract must stop making an unqualified claim that every no-report child is technically read-only. Instead they should state exactly which Tasks lack Bash and which Bash-enabled Tasks have unsandboxed execution authority.

This proposal does not authorize implementation agents or intended repository mutation. A future enforceable mutation capability requires a separate decision.

### Web search and fetch

`web_search` and `fetch_content` are independently selectable. Requesting either changes a Task from local-only analysis to external research.

- `web_search` discovers and synthesizes cited external sources through the authenticated Codex provider owned by `pi-web-access-minimal`.
- `fetch_content` retrieves a known public HTTP(S) source through that package's network trust boundary.

No fallback provider or silent capability substitution is permitted.

### Report writer

`write_report` remains closure-bound to one validated path and is supplied only because `reportPath` exists. It cannot be requested in `tools` and is unaffected by caller ordering.

## 10. Web-provider integration

The sibling repository `/Volumes/Code/Personal/pi-extensions/pi-web-access-minimal` already owns and tests the network trust boundary and internally exports factories for `web_search` and `fetch_content`. Its package is currently private and does not expose a public library export suitable for a sibling package import.

The proposed integration is a narrow versioned in-process provider protocol over Pi's shared extension event bus. It avoids:

- copying the web implementation;
- importing a sibling checkout by absolute path;
- making web access a mandatory package dependency;
- loading arbitrary parent/global extensions in child sessions;
- pretending `pi.getAllTools()` metadata contains executable tool implementations.

Conceptual provider contract:

```ts
type WebToolName = "web_search" | "fetch_content";

type WebToolProviderV1 = {
  schemaVersion: 1;
  createTools(names: readonly WebToolName[]): ToolDefinition[];
};
```

At Delegation preflight, `pi-subagents-minimal` sends a provider request containing a response callback. `pi-web-access-minimal` responds if loaded. A request-time handshake avoids extension load-order dependence.

Preflight must verify:

1. a provider exists when a web tool is requested;
2. exactly one supported provider responds;
3. the provider protocol version is supported;
4. every requested tool is returned exactly once;
5. returned definitions have exactly the expected names;
6. required authentication/model availability is established where possible;
7. no Delegation id or runtime state exists after failure.

The provider should return fresh definitions or otherwise own safe dependency sharing. Once admitted, those definitions become part of the child's fixed execution contract. A later execution failure is a child run failure; the extension never silently removes a requested tool.

Open technical question for review: whether callback-bearing event-bus messages are the best supported Pi extension-to-extension service mechanism, or whether a smaller exported shared contract is preferable without introducing package-resolution coupling.

## 11. Child runtime and isolation

The child continues to use:

- a fresh in-memory `SessionManager`;
- in-memory settings;
- the resolved model and exact Thinking level;
- a restricted `DefaultResourceLoader`;
- no discovered child extensions, skills, prompt templates, or themes;
- repository-bounded context files;
- the exact package-owned Subagent definition;
- the exact effective tool allowlist.

Web ToolDefinitions are passed directly as child custom tools. The child does not load the full web extension or any other global/project extension.

A Flat batch resolves capabilities independently per child. A web-enabled Research Task does not grant web access to its siblings.

## 12. Terminal envelope and persistence

New child outcomes should record the complete canonical effective tool list:

```ts
type ChildOutcome = {
  index: number;
  outcome: "succeeded" | "failed" | "timed_out" | "cancelled";
  effectiveModel: `${string}/${string}`;
  effectiveThinking: ThinkingLevel;
  effectiveTools: EffectiveToolName[];
  // existing result/report/partialResult/error/truncation fields
};
```

Capability metadata is protected, non-truncatable content. Preflight feasibility and canonical envelope allocation must reserve it. Completion order and caller tool order must not affect serialization.

Existing `0.1.0` persisted Terminal envelopes lack `effectiveTools`. They must remain inspectable and byte-identical; they must not be silently rewritten. The implementation must explicitly distinguish legacy persisted entries from new entries.

Open specification question for review:

- use persisted `schemaVersion: 2` for new envelopes and reconstruct both versions; or
- retain `schemaVersion: 1` because the package is unpublished, while accepting a documented legacy pre-release shape.

The proposal currently prefers a new persisted schema version because `effectiveTools` is required for truthful new outcomes, but the reviewer should challenge whether that creates unnecessary pre-v1 complexity.

## 13. Versioning and canonical-source changes

This is a Significant behavioral change. It alters:

- public Task schema;
- package-owned Agent identity and instructions;
- capability isolation;
- result projection;
- persisted metadata;
- participating parent skills.

The dogfood package should move from `0.1.0` to `0.2.0`.

Before executable changes, create a specification issue under GitHub issue #18. That issue should explicitly supersede affected parts of issue #5 and the current contract.

If approved, update:

## 14. Parent-skill integration

Parent skills remain external and own workflow prompts.

Expected integration behavior:

- direct exploration defaults to base local inspection and requests Bash only when Git or executable checks are material;
- research requests `web_search` and/or `fetch_content` when external primary sources are required;
- `code-review-diff` requests Bash for fixed-point diff inspection;
- `code-simplify` requests Bash for working-tree diff inspection;
- each reviewer Task names its temporary lens in `task`;
- no parent skill supplies an arbitrary system prompt or capability outside the closed enum.

Participating-skill changes are part of the Significant behavioral change and must be reviewed with the extension, even though the skills are not bundled.

## 15. Deterministic evidence plan

Every executable behavior must first receive defect-revealing red proof anchored to the approved specification.

Required evidence includes:

### Schema and preflight

- Tasks no longer accept `agent`;
- omitted/empty `tools` receives only base tools;
- each legal additional tool is accepted;
- duplicate and unknown tools fail before id allocation;
- unavailable/malformed/ambiguous web providers fail before admission;
- batch children resolve tools independently;
- protected effective-tool metadata participates in feasibility checks.

### Prompt and definition

- the exact Task string becomes the child user prompt unchanged;
- prompt templates and skills remain disabled;
- packaged `agents/subagent.md` bytes equal the approved fixture;
- the definition contains generic discipline and no workflow-role bias.

### Runtime capabilities

- exact built-in and custom tools reach each child;
- Bash is absent unless requested;
- web tools are absent unless requested;
- selected web tools execute through provider-owned definitions;
- `write_report` appears only with `reportPath`;
- sibling capability sets do not leak;
- nested delegation remains unavailable.

### Projection and persistence

- every new child outcome records canonical `effectiveTools`;
- requested order cannot alter output bytes;
- allocation remains UTF-8 bounded and completion-order independent;
- legacy `0.1.0` envelopes reconstruct byte-identically;
- new schema entries survive reload and consumption-marker behavior.

### Web-provider repository

- provider handshake works regardless of extension load order;
- provider version/name validation fails closed;
- factories return the exact requested definitions;
- existing network/auth/trust-boundary behavior remains owned by web-package tests;
- no provider request starts network or disk work prematurely.

### Budgets and packaging

- parent tool payload and prompt remain under hard ceilings;
- reviewed baselines are updated only with justification;
- packed artifacts contain only allowlisted files/dependencies;
- optional web absence does not break local-only Delegations.

## 16. Model evaluation plan

Deterministic tests cannot establish that a generic system prompt plus parent-owned Task prompts produces useful model behavior.

After implementation, run one small Recorded evaluation at the intended default model and Thinking level using the actual parent skills:

1. repository exploration with base tools;
2. external evidence-intensive research with web tools and a declared report;
3. Standards/Spec diff review with Bash;
4. Reuse/Quality/Efficiency simplification with Bash.

Capture:

- concrete behavioral question;
- source commit and package versions;
- Pi/provider/model/Thinking versions;
- exact parent requests;
- exact generated Task strings;
- requested and effective tools;
- Terminal envelopes and reports;
- predeclared workflow-specific criteria;
- conclusion and uncertainty.

One representative run per workflow is sufficient initially. Repeat only after correcting a concrete prompt/oracle ambiguity or investigating a failure. This evidence is human-reviewed supporting material under ADR 0001, not CI, release qualification, or a restored Behavioral battery.
