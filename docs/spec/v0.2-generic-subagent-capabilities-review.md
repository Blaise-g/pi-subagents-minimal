# Review: Generic Subagent and Selectable Capabilities Proposal

Status: **Historical design evidence; not normative**

Normative implementation specification: [Canonical implementation contract](v1-implementation-contract.md)

Reviewed document: `docs/spec/v0.2-generic-subagent-capabilities-proposal.md` (draft reviewed 2026-08-28)

Reviewer stance at review time: independent; the proposal was not assumed approved.

Intended consumer models: primarily GPT-5.6 (`gpt-5.6-luna|terra|sol`), possibly Claude. Where this changes a recommendation it is called out.

Each finding is labelled **Defect** (factual error or internal contradiction), **Recommendation** (I would push back and do something else), or **Open** (genuine uncertainty). "Verdict" lines say whether I agree, push back, or want a decision.

Sources checked beyond the proposal: `CONTEXT.md`, `docs/spec/v1-implementation-contract.md`, `agents/investigation.md`, `src/runtime.ts`, `src/index.ts`, `src/projection.ts`, `docs/research/gpt-5-6-codex-subagent-guidance.md`, `.worktrees/candidate-designs/docs/research/candidate-subagent-designs.md`, the sibling `pi-web-access-minimal` sources, the installed Pi `0.84.x` SDK (`node_modules/@earendil-works/pi-coding-agent/dist/**/*.d.ts`, `docs/extensions.md`, `docs/sdk.md`, `docs/packages.md`), and external references listed in the appendix.

## A. Summary judgment

**`approve with changes`.**

The core move — one fixed execution profile, the analytical role carried in `task`, a closed package-owned capability enum, no Agent catalog, no arbitrary system prompt or tool forwarding — is right and is supported by the repo's own evidence (role-shape prototype found no correctness gain from specialised definitions; candidate-designs research rejected catalogs and fuzzy substitution). The changes I would require before writing the normative contract are: (1) do not ship the unguarded built-in `bash` as the answer to "inspect a diff" — ship a guarded shell or a `git` inspection tool so the review workflows stay technically report-only; (2) for the web provider, spike the one runtime unknown (does a child custom tool receive a working `ctx.modelRegistry`?), fix the `fetch_content` variant decision (plain tool, no continuation in children), and stage web access as its own release if that is not resolved quickly; (3) adopt `schemaVersion: 2` for envelopes; (4) accept duplicate `tools` entries idempotently rather than rejecting them. Everything else is refinement.

## B. Domain model (§5)

**Verdict: agree with the separation; three terms need fixing.**

1. **Defect — the `Investigation` term is left undefined.** §5 introduces Subagent, Subagent definition, Task role, Base/Additional capability, Derived report capability, Effective tools, but says nothing about `Investigation`, which is currently a first-class glossary term (`CONTEXT.md` "Investigation"), the noun in the `delegate` description (`src/index.ts:82`), the title of `agents/investigation.md`, and used six times in `README.md`. The proposal's whole argument is that "investigation" wrongly implies a role, so the term must be either retired or redefined as "the name of the 0.1.0 profile". §13 lists `CONTEXT.md` as an update target but not what happens to this term. Add it explicitly; otherwise the glossary and the tool description drift.

2. **Recommendation — pick one word: "capability" or "tool".** §5 says *Additional capability*, §6 types it `AdditionalTool`, the field is `tools`, §12 records `effectiveTools`. Three names for one concept will leak into error codes, tests and docs. I would use **tool** everywhere in the schema/envelope (`tools`, `AdditionalTool`, `effectiveTools`) and keep "capability" only as prose for the *set* ("capability set"), which is how `CONTEXT.md` already uses it in the Subagent entry.

3. **Recommendation — "Task role" is fine but define its negative space.** The glossary entry should say it "grants no capability, selects no definition, and is not validated" so that nobody later adds a `role` field. Also consider "Task lens", since the proposal itself says "role or lens" (§5, §7); one word is enough.

4. **Recommendation — add a `Web tool provider` term** if §10 survives (the extension that answers the capability request), and a `Guarded shell` / `Git inspection` term if D.1 is adopted. Missing glossary terms for things that appear in the contract is how the previous glossary ended up with "Agent definition" meaning something the package never actually exposed.

5. Clean separation check: *Subagent* (execution entity) vs *Task role* (prompt content) vs *Additional tool* (enum) vs *Effective tools* (canonical realised list) are separated cleanly. The one blur is §5 "Subagent definition … does not define the child as a Researcher, Explorer, or Reviewer" — this is a constraint on the file, not a definition; move it to §8.

## C. Public schema (§6)

**Verdict: agree on removal of `agent`, the closed enum, omission semantics; push back on duplicate rejection; one budget consequence is missing.**

1. **Agree — remove `agent: "investigation"`.** A single-literal field is not a selector, and the repo's own contract admits it ("no Agent-scope or Agent-discovery argument", contract §3.1). It also removes an `AGENT_UNKNOWN` error path and a few schema bytes. Claude Code's `Agent` tool and Tintinweb both use a real selector because they *have* a catalog; this package deliberately does not, so mirroring the field is cargo. If a future catalog is ever wanted, adding an optional field is a compatible minor change; keeping a dead literal buys nothing now.

2. **Agree — `tools?: AdditionalTool[]` as additions-only over an implicit base.** This matches the least-authority default and keeps calls short for the common exploration case. Naming it `tools` matches the Claude Code agent frontmatter and the Codex/Pi `--tools` vocabulary, which helps model priors.

3. **Push back — reject duplicates → dedupe instead (Recommendation).** Rejecting `["bash","bash"]` costs the Orchestrator a full failed `delegate` round trip to correct something that has exactly one meaning. The project's "fail rather than substitute" rule exists to stop *silent semantic changes*; deduplication is not a semantic change, and the persisted `effectiveTools` already records the truth. With GPT-5.6 orchestrators the cheaper failure mode matters more than schema pedantry. Keep **unknown names → preflight failure** (that *is* semantic). If you want strictness for free, `Type.Array(StringEnum(...), { uniqueItems: true })` produces Pi's standard schema-validation error (Pi validates tool arguments with TypeBox `validateToolArguments`) without a custom code — acceptable, but I would still prefer dedupe.

4. **Agree — canonical order `read, grep, find, ls, bash, web_search, fetch_content, write_report`; caller order irrelevant.** Note that this list changes if D.1 is adopted (`git` or `shell` instead of/in addition to `bash`).

5. **Missing consequence (Defect by omission)** — the new `tools` enum and any reworded `delegate` description change the provider-facing tool JSON, which is gated by `test/context-budget.test.ts` against `budgets/context-baselines.json` (10 % drift rule in `docs/context-budget-protocol.md`). §13/§15 do not mention a baseline update. Add it, and keep enum descriptions terse (one clause each) so the launch-only budget stays within the 4 KiB ceiling.

6. **Open → position: the per-call `tools` enum has no direct precedent; keep it, but argue it as a deliberate choice.** Nothing mainstream exposes a caller-selectable closed set of *extra* tools per call: Claude Code's `AgentInput` has no tools field (tools live in the agent definition's `tools`/`disallowedTools`); Codex documents per-spawn overrides only for model and effort (capabilities live in the agent TOML, e.g. `sandbox_mode`, `mcp_servers`); the Responses multi-agent beta gives every agent the root request's tools; Gemini/Cursor are frontmatter-or-inherit. The only caller-passed tools array in the field is Arhen's arbitrary allowlist — the model the proposal rejects. The definition-owned alternative would be two or three package-owned *profiles* selected by name (`local`, `local+git`, `research`). I would still keep the enum: with three additions the combination space is tiny, "base + additions" is shorter for the common case than naming a profile, and `effectiveTools` records the result truthfully. But the ADR (§13) must say this is a novel position between "definition-owned" and "arbitrary forwarding", not claim precedent. Related: §4 cites Nico `0.57.0` and Tintinweb `0.18.2`; both have since moved (`0.58.0`, `0.19.0`, 2026-08-27) without changing the authority model — refresh the citation, no argument changes.

7. **Missing field check:** nothing is missing for 0.2. Do **not** add `cwd`, `timeout`, `systemPrompt`, or per-task deadlines — all are excluded by the contract and by the research conclusions. `model`/`thinking`/`reportPath` semantics are unchanged and should stay so.

## D. Capability and security boundary (§9)

**Verdict: the truthfulness correction is right; push back on shipping unguarded built-in `bash`; two web-tool risks are undocumented.**

### D.1 Bash — the biggest push-back

**Recommendation.** §3 motivates `bash` with two different needs: (a) *inspect a Git diff* for `code-review-diff` / `code-simplify`, and (b) *run checks* for "selected reviews". Only (b) needs a shell. Giving the review workflows the built-in `bash` to satisfy (a) means the flagship "report-only" reviews become children with unsandboxed execution, network, and host-credential access (the proposal acknowledges this in §9 — that honesty is good, but it is a reason to change the design, not just the docs). The repo's own candidate-designs research already concluded: "'report-only' must be an enforced tool allowlist, not merely a role prompt. Prefer no `bash` for read-only roles unless a workflow battery proves it necessary."

A concrete, previously unnoticed conflict: a `code-simplify` reviewer that runs a check (`bun test`, `npm run build`) mutates the working tree it is reviewing (caches, build output, lockfile touches), so **need (b) corrupts need (a) inside the same Task**. Bash-for-checks and diff inspection should not be the same capability.

Pi gives three enforceable options, all verified against the installed SDK:

- **Option 1 (preferred for 0.2): `git` inspection custom tool**, closure-bound like `write_report`: `spawn("git", [...argv])` with no shell, `cwd` = repository root, a subcommand allowlist (`diff`, `log`, `show`, `status`, `blame`, `rev-parse`, `ls-files`, `merge-base`), `--no-pager`, and a denylist for options that write or execute (`--output`, `--ext-diff`, `--textconv`, `-c`, `--exec-path`, `-C`, `--git-dir`, `--work-tree`, `--config-env`) plus `GIT_CONFIG_*` env scrubbing. It exactly serves `code-review-diff` (fixed point) and `code-simplify` (working tree), has a package-owned description (so capability policy lives in the tool description, not the fixed definition — see F), and keeps the review workflows technically report-only. It is not zero-risk (git has many escape hatches), but the surface is enumerable and testable, unlike `bash`.
- **Option 2: guarded shell.** Pi lets a `customTools` entry named `bash` shadow the built-in (`agent-session.js` builds built-ins first, then `customTools` override), and `createBashToolDefinition(cwd, { operations, spawnHook })` is public. Alternatively an inline `extensionFactories` entry — which **loads even with `noExtensions: true`** (`resource-loader.js`, factories load unconditionally) — can register a child-side `tool_call` handler returning `{ block: true, reason }`. Either gives a real enforcement point for a command allowlist. This is more work and command-allowlists for shells are notoriously leaky; use it only if (b) is actually needed in 0.2.
- **Option 3: ship built-in `bash` as proposed** but name it truthfully and narrow the claims. If you take this route the enum value should carry its own warning in the JSON-schema description, the README must stop saying reviews are report-only, and the no-implementation-agent sentence in §9 should be rewritten as "the package grants no mutation *by design*; `bash` is an unsandboxed escape hatch whose consequences are owned by the requesting parent".

I would ship Option 1 in 0.2 and defer (b) ("run checks") to a later decision with Option 2 as the enforcement mechanism. If the maintainer insists on a shell now, Option 2 over Option 3.

**Prior art (verified 2026-08-28).** Every vendor that ships a read-only agent with shell access enforces it technically, never by prompt: Codex per-agent `sandbox_mode = "read-only"` (Seatbelt / bubblewrap+seccomp; "the sandbox applies to spawned commands… `git`, package managers, or test runners inherit the same sandbox boundaries"; their own example agent is `pr_explorer`, a read-only codebase explorer); Cursor `readonly: true` per subagent; OpenCode per-agent `permission.bash: {"git diff": allow, "git log*": allow, "*": ask}` — the literal git-inspection allowlist; Claude Code's `Explore` agent denies `Write`/`Edit` and its read-only bash set includes "read-only forms of `git`" and "is not configurable". Every vendor shipping *pattern* allowlists also documents the leaks (compound commands, `-c` making git run a program, wrapper smuggling), which is why Option 1's fixed argv + option denylist is preferable to a command-string filter. Pi offers neither an OS sandbox nor per-child bash pattern rules, so raw `bash` really is unsandboxed authority.

**Model note.** OpenAI's GPT-5.6 guide: "For requests to answer, explain, review, diagnose, or plan, inspect the relevant materials and report the result. Do not implement changes unless the request also asks for them", and "Repeating instructions such as 'ask first,' 'do not mutate,' or 'wait for approval' can cause unnecessary approval requests for safe, expected actions." Both point the same way: enforce by tool set, state the boundary once in prose.

### D.2 Read-only language

**Agree (Defect in current docs, correctly identified).** README "Without one, an Investigation is read-only" and contract §1 "Read capability is not a filesystem sandbox" are already in tension; §9 correctly says the unqualified read-only claim must go. Replace with a per-tool matrix (see G/H) and the sentence "children without `bash`/`git` have no mutation tool; `write_report` mutates exactly one declared path".

### D.3 Web tools

**Agree in principle; two risks must be documented (Recommendation).**

- **Exfiltration channel.** A child with `read` + `fetch_content` can encode repository content into a URL query string. The web package's trust boundary (public-IP policy, size caps) does not prevent this — it is a *data-egress* boundary, not a *data-loss* boundary. The Orchestrator has the same channel, but the child runs unattended in the background with no UI. Document it as an accepted risk of requesting `fetch_content`; it is not a blocker.
- **Disclosure via search.** `web_search` sends the query to the Codex provider. Prompt-injected or careless children may put repository content into queries. Same treatment: document; parent skills should say what may be searched.
- `web_search`'s `execute` resolves credentials through the **child's** `ctx.modelRegistry` (`pi-web-access-minimal/src/search-auth.ts` `SearchRegistry`, `src/tools.ts`). Preflight item 6 ("authentication established where possible") is therefore not just "nice to have" — see E.3.

### D.4 Report writer

**Agree.** Keeping `write_report` derived, not selectable, is right. One defect to catch in tests, not the spec: the current allowlist logic is `tools: request.customTools ? [...base, "write_report"] : base` (`src/runtime.ts:23`). Once web tools are also `customTools`, that conditional would enable `write_report` for a web-enabled Task **without** `reportPath`. The proposal's §15 "write_report appears only with reportPath" catches it if the test is a *negative* case with web tools present and no `reportPath`. Make that explicit.

## E. Web-provider protocol (§10)

**Verdict: the seam choice is correct and now verified; two runtime unknowns should be resolved by a spike before the contract is written; consider staging.**

### E.1 Is the event bus the right mechanism? — Yes (Open question in §10 resolved)

Verified against Pi `0.84.x` source:

- `pi.events` is a plain in-process `EventEmitter`; `emit(channel, data: unknown)` passes the payload **by reference**, so `ToolDefinition` objects with closures and a reply callback travel intact. Dispatch is **synchronous**; `emit` returns `void` and does not await handlers; async handler errors are swallowed. Consequence: the provider's listener must be **synchronous** and call `reply(...)` inline, and the consumer must treat "no reply by the time `emit` returns" as "no provider".
- The bus is shared by all extensions loaded through one `ResourceLoader` (one session). The child's loader creates its own bus, which is fine — the handshake happens parent-side.
- `pi.getAllTools()` returns `Pick<ToolDefinition,"name"|"description"|"parameters"|"promptGuidelines">` — no `execute`. The proposal's rejection of that path is correct.
- Cross-package `import` is unsupported by design: Pi docs state packages load with *separate module roots* and other pi packages must be **bundled** (a copy). So "smaller exported shared contract" (§10's alternative) is not available without vendoring, which the proposal rightly rejects.
- No Pi docs example exists of one extension providing a *service* to another; the only inter-extension example is one-way notification. You are on a supported primitive but an undocumented pattern — say so in the ADR.

So: **callback-in-payload over `pi.events`, requested at Delegation preflight (never in the factory body), is the best available seam.** Concrete protocol notes:

- Request payload: `{ protocol: "pi-web-access-minimal/tools", version: 1, names, reply(result) }`. Include a `providerName` in the reply so ambiguity (two responders) is detectable and reportable.
- Because dispatch is synchronous, "exactly one responder" is a simple counter after `emit` returns; no timeout needed for the handshake itself.
- **Fresh definitions per request** is the right lifecycle; shared `FetchDependencies` (retention store) inside the web package is already a memoised singleton (`src/tools.ts` `defaultDependencies`), so sharing is provider-owned as the proposal wants.

### E.2 Which `fetch_content`? (Defect by omission)

The web extension registers `createContinuationFetchContentTool(...)` plus a dynamically activated `continue_extraction` tool driven by `pi.setActiveTools` in the **parent** (`extensions/web-access-minimal.ts`). Neither continuation nor dynamic activation exists in the child. The provider must return the plain `createFetchContentTool` and the contract must state that **truncated fetches are not continuable inside a child**. Also note the retention store writes extracted text to disk under the web package's directory; that is a mutation outside the repository that the "no mutation" language must not deny.

### E.3 Child `ctx.modelRegistry` (Open — verify by spike, then it becomes a blocking item in J)

`web_search` needs `ctx.modelRegistry.getAll()` / `getApiKeyAndHeaders()` from the *child's* `ExtensionContext`. The child is built with `createAgentSession({ modelRuntime: ModelRuntime.create() })`; the registry should be the runtime's, sharing `auth.json`, so this most likely works — but it is the one execute-time dependency that can make an admitted Task fail at first tool call with a confusing "run /login" message. Spike it (one child, one `web_search` call) before the contract promises preflight item 6. If the registry is present, preflight can also call the provider's own `resolveSearchCredentials` equivalent through a `probe()` hook; if not, drop item 6 and document the failure mode.

### E.4 Staging (Recommendation)

The provider protocol is the only part of 0.2 that touches a second repository with its own release discipline, a private package, and a shared conceptual contract. I would split: **0.2.0** = generic definition + `tools` enum + local capability (`git` and/or guarded shell) + `schemaVersion: 2`; **0.3.0** = web provider on both sides. Both can land in the same dogfood month, but decoupling means the review/simplify claims in README get fixed without waiting on E.3, and the web repo's change gets its own spec issue. If research with web is the *more* urgent need, invert the order — the point is not to couple them.

## F. Prompting and instruction ownership (§7, §8)

**Verdict: agree on the generic definition, opaque Task string, no semantic linting, and the ownership split; four edits to §8.**

1. **Agree — generic definition.** Consistent with the role-shape prototype (no correctness difference between one definition and specialised ones) and with OpenAI's lean-prompt guidance. Claude Code's `Explore`/`Plan` agents are the counter-model (catalog with per-agent prompts) but they exist because Claude Code ships the roles; this package explicitly delegates roles to external skills. Either model is coherent; the proposal picks the one consistent with its boundary.

2. **Recommendation — remove future-tense policy from the definition.** §8 item 5 "avoid intentional repository mutation unless a future explicit mutation contract authorizes it" puts governance language into a model prompt. Write the boundary once, in present tense: "Do not modify files, Git state, or configuration. Read-only commands are permitted when a shell or Git tool is supplied." That follows the GPT-5.6 guide's "one compact policy that names safe actions explicitly" and avoids the over-refusal it warns about.

3. **Recommendation — keep capability-specific rules in tool descriptions, not the fixed definition.** The definition is byte-tested and identical for every child, so any line about `bash`/`web_search` is present even when the tool is absent — the opposite of "expose only task-relevant tools". `write_report` already carries its own rules in its description; do the same for `git`/shell and for web tools (the web package's descriptions are already self-sufficient by design). The definition then needs only the generic sentence in F.2.

4. **Recommendation — §8 item 3 "when material"** weakens the current text ("Clearly distinguish facts, recommendations, and uncertainty"). Keep the current unconditional wording; conditional epistemics are exactly what a GPT-5.6 child will use as licence to omit caveats.

5. **Agree — opaque `task`, no linting.** Heuristic prompt linting would be non-deterministic to test and would fight the parent skills. Put the §7 "well-framed Task" checklist in README/parent-skill guidance, **not** in the `delegate` description (budget).

6. **Model note.** For Claude children, Anthropic's multi-agent research write-up says "Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries. Without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information" — which is §7's list verbatim. The "definition-owned system prompt + caller-supplied task string" split is also the mainstream pattern (Claude Code: "The only content you pass from parent to subagent is the Agent tool's prompt string"; Codex `developer_instructions` in the agent file; Gemini, Nico, Tintinweb likewise — Arhen's inline `prompt` is the sole outlier). Codex's generic built-ins (`default`, `worker`, `explorer`) and Claude Code's (`general-purpose`, `Explore`, `Plan`) are the closest precedent for a generic profile rather than a persona catalog. Nothing here is GPT-specific; the split works for both families. One GPT-5.6-specific caution: the model "tends to be more concise by default than GPT-5.5", so §8 item 6 ("return the concise requested answer") should specify what a short answer must preserve (conclusion, evidence, caveat) rather than just ask for brevity.

## G. Persistence and compatibility (§12)

**Verdict: `schemaVersion: 2`. Minimum safe legacy policy below.**

**Recommendation — `schemaVersion: 2` for new envelopes.** Reasons: (1) `effectiveTools` is required for truthful new outcomes, and a required field on version 1 would make every old entry non-conforming; making it optional instead makes it optional forever. (2) Only package-owned code parses envelopes, so the cost is one discriminated branch in `parseEnvelope` plus fixtures — small. (3) It matches the contract's own versioning rule ("persisted data that cannot be read transparently" is major; a readable additive version bump is minor). (4) Bumping now, while unpublished, is the cheapest it will ever be.

**Minimum safe legacy policy:**

- `parseEnvelope` accepts `schemaVersion: 1` (no `effectiveTools`) and `2` (required `effectiveTools`). Anything else → `PERSISTED_ENTRY_UNREADABLE` diagnostic, as today.
- v1 entries reconstruct **byte-identically** and are never rewritten; do **not** synthesise `effectiveTools: ["read","grep","find","ls"]` for them — that would be a claim the record never made.
- `delegation_control` inspection returns whichever version was persisted; the parent can tell them apart by the field.
- Add a mixed-branch fixture (one v1 terminal + marker, one v2) to `test/recovery.test.ts`.
- Leave `AcceptedDelegation.schemaVersion` and `LiveInspection.schemaVersion` at 1 unless their shapes change (they don't).

A pre-release "wipe legacy entries" policy is *acceptable* given the package is unpublished, but it contradicts contract §2.3's "reads all earlier persisted entries or fails explicitly" and buys almost nothing; keep the contract.

## H. Verification adequacy (§15, §16)

**Verdict: the list is good; these cases are missing or weakly specified.**

### Missing deterministic cases

1. **Web tools without `reportPath` must not enable `write_report`** — the conditional at `src/runtime.ts:23` is exactly this bug shape (see D.4).
2. **Provider tool throws at execute** → child outcome `failed` with `error.stage: "run"`, never a Host diagnostic, and the effective tool list still records the tool (the proposal's "never silently removes a requested tool").
3. **Provider replies asynchronously / twice / after preflight returns** → ignored, no retained reference, no id allocated. (Synchronous bus makes this testable with a fake provider.)
4. **Zero, two, or version-mismatched providers** → distinct preflight codes (`WEB_PROVIDER_MISSING`, `WEB_PROVIDER_AMBIGUOUS`, `WEB_PROVIDER_UNSUPPORTED`), no id.
5. **Provider returns extra/missing/duplicate names** → fail closed.
6. **Exact allowlist per child**: assert the *complete* set (`edit`, `write`, `powershell`, `delegate`, `delegation_control` absent), not just presence of requested tools. Note `powershell` is a built-in name in Pi 0.84.x — it must be excluded on Windows too.
7. **Custom-tool shadowing**: if a guarded `bash`/`git` custom tool is shipped, assert the built-in is not also reachable.
8. **Feasibility with maximal metadata**: preflight must reserve the longest `effectiveTools` array (all names present) for every child; test a batch of 8 children each with all tools plus maximal report paths still admits or rejects deterministically.
9. **Permutation invariance of `tools`**: `["bash","web_search"]` vs `["web_search","bash"]` → byte-identical envelope.
10. **Mixed v1/v2 branch reconstruction** (see G).
11. **Context-budget**: new schema and descriptions vs `budgets/context-baselines.json`, with the reviewed baseline update recorded.
12. **Sibling isolation**: batch `[ {tools:["web_search"]}, {} ]` → child 2's registered tool names exclude `web_search` (currently only implied).
13. **Bash/git cwd**: the child's shell/git cwd equals `ctx.cwd` (or repo root for `git`), not the extension's `import.meta` dir.

### Weak oracles

- §15 "the definition contains generic discipline and no workflow-role bias" is not a deterministic oracle. Byte-equality to the approved fixture is sufficient; drop the vague clause or replace it with a negative word-list (`Investigat`, `Researcher`, `Explorer`, `Reviewer`) — cheap and deterministic.
- "required authentication/model availability is established where possible" (§10 item 6) is not testable as written; either specify the `probe()` contract or delete it (see E.3).

### Model evaluation (§16)

Agree with one representative run per workflow under ADR 0001; it does not recreate a release gate. Two additions:

- **Predeclare at least one Claude-model child run** (or record why not), since Claude is a stated possible consumer. Same Task strings, same tools; the question is whether the generic definition + parent prompts transfer across families.
- **Add a mutation oracle** for any shell/git-enabled run: `git status --porcelain` before and after must be identical. It is the one behavioural claim in this proposal ("no intentional mutation") that has a cheap deterministic check.

## I. Scope and minimality

**Remove from 0.2.0 / defer**

- Built-in unguarded `bash` (replace with `git` inspection tool; defer "run checks" to a guarded-shell decision — D.1).
- Web provider → 0.3.0 unless E.3 spikes green quickly (E.4).
- §10 preflight item 6 (auth probe) until the provider exposes a probe.
- Continuation for fetched content in children (state it is unavailable — E.2).
- Duplicate-entry rejection (simplify to dedupe — C.3).

**Simplify**

- One vocabulary word (`tool`) across schema, envelope, and glossary (B.2).
- Definition: generic sentences only; capability policy in tool descriptions (F.3).

**Supposedly deferrable but actually necessary for truthful initial support**

- **README/contract claims** about review and simplification must be reconciled in 0.2 regardless of which capability ships — today the README advertises both workflows and the contract calls them "report-only" while the only local diff mechanism is an embedded diff in `task`. Either ship `git` in 0.2 or narrow the README now.
- **The `Investigation` term** decision (B.1) — leaving it in the `delegate` description while removing it from the schema is a mismatch visible to the model.
- **Context-budget baseline update** (C.5).
- **`schemaVersion: 2` parsing** (G) — required the moment the first 0.2 envelope is persisted.

## J. Blocking questions

Only decisions that must be resolved before the normative spec or code:

1. **Local capability for reviews: `git` inspection tool, guarded shell, or built-in `bash`?** (D.1). Determines the enum, the tool descriptions, the README claims, and the mutation oracle.
2. **Is web access in 0.2.0 or 0.3.0?** (E.4). If 0.2: **spike E.3** (`ctx.modelRegistry` in a child custom tool) and pick the plain `fetch_content` variant (E.2) first.
3. **Envelope `schemaVersion: 2`** — confirm (G). Everything in §12/§15 persistence depends on it.
4. **Fate of the `Investigation` term** in glossary, `delegate` description, agent filename (B.1).
5. **Duplicate `tools` semantics** — dedupe vs reject (C.3). Small, but it changes an error code and a test.

Not blocking (can be settled in the spec issue): word choice tool/capability, §8 wording edits, model-evaluation matrix, provider error-code names.
