Minimal background lifecycle

Drive a proposed parent-facing contract: one always-available launch tool and one control tool that exists only while a Delegation is live or has an unread terminal result.

Question: Does a dynamically exposed delegation_control tool—combining truthful inspection/result access with whole-Delegation cancellation—provide enough control without paying for permanent status, result, wait, and cancel tools?

Current parent surface

Only observed states are named: queued (registered, prompt not accepted), running (Pi accepted the child prompt), cancelling (abort requested, settlement pending), and terminal. There is no percentage, ETA, “stalled,” or inferred progress.

    Contract this prototype is testing

    • delegate launches exactly one Subagent or one Flat batch and immediately returns one Delegation id.
    • delegation_control is activated after launch. inspect returns a truthful live phase or the bounded terminal result; cancel requests cancellation of the whole Delegation.
    • A small completion message announces only that a Delegation became terminal. The potentially larger result enters model context only when inspected.
    • After every live Delegation is terminal and every terminal result has been inspected, the control tool is removed from the active tool set.
    • The registry is session-memory only. Parent shutdown cancels and settles live work; v1 has no resume, persistence, steering, per-child controls, or polling-only status tool.
